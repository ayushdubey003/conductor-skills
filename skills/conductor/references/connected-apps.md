# Connected Apps

The cluster stores a named connection. The connection determines the provider identity. A name containing “test” does not prove which provider account it reaches. Clarify an ambiguous target before writing. Authoring a task makes zero provider calls. If a one-off action would require saving a workflow, ask before creating it.

## Discover what the cluster supports

If the user reports that `conductor integration types` rejected the selected profile, quote the error and stop. This also applies when the same request asks for a workflow. Changing profiles or server type, probing with another client, and drafting or saving a workflow all require a new request.

Use the selected CLI profile for discovery and changes. Run `conductor integration --help` or `npx @conductor-oss/conductor-cli integration --help`. If neither provides the integration commands, report that limitation. The bundled Python helper does not implement Connected Apps discovery.

To map a requested action to an operation, run `conductor integration types --json`. Pick the matching provider from the entries with `category: MCP` (Connected Apps), then inspect `conductor integration operations --type <type>`. Match both the action and resource. A type's catalog is useful before credentials exist. For a chosen connection inspect its own operation and input/output schema with `conductor integration operations <connection> --name "<exact operation>"`. Ask for each missing required operation input before building the task. For example, if the schema requires a region, ask which region to use or bind it to a workflow input. A saved connection identifies the credentials; its name does not supply the region. If the schema is unavailable, stop before constructing the task. A successful lookup can return an empty catalog. Do not guess a method, use an HTTP/custom worker as a silent substitute, or probe a provider's inventory to design a workflow.

Pass the exact type ID returned by the catalog to `conductor integration list --type <type> --json` to find visible saved connections. Honor a named eligible connection. For workflow creation use the sole eligible connection automatically and identify it in the result. Ask which to use when several qualify. Offer setup if none qualifies. For a *setup* request, offer reuse or creation even with one eligible connection; wait for the choice. If the user already specified a new connection, proceed to its configuration.

## Saved integrations

- **Create.** Read `conductor integration type-config <type>`. Collect the name, supported auth mode and only the applicable fields. Keep operation inputs with the workflow. Summarize the non-secret settings and ask “Create <connection name> on <cluster> using <auth mode>?” Wait for a separate yes before saving, including when the mode uses the worker identity and has no credential fields. Choosing the mode supplies a field value, not consent to create the connection. Use `conductor integration create --file <protected-file>` or stdin, with name, type, enabled, description and configuration. Omit the category to use the one registered for the provider type. Verify by name. Reuse and cancellation make zero writes; a collision is a choice for the user.
- **Read.** When asked for a list and details, run `conductor integration list --type <type> --json` first, then inspect the named match with `conductor integration get <name>`. Report accessible metadata and configured field names. Never inspect raw provider GET responses to obtain secrets.
- **Update.** Read the named connection. Send only changed fields with `conductor integration update <name> --file <protected-file>` or stdin, e.g. `{"description":"Finance receipts"}`. Configuration patches merge by field name. A changed field takes the supplied value in full. Do not send masked credentials, empty placeholders, or a reconstructed configuration. Verify metadata with get; never claim a rotated credential works at the provider without separate evidence. Check CLI help if update is unavailable; explain the limitation instead of deleting/recreating the connection.
- **Delete.** Identify the cluster, exact connection and known workflow impact; disclose if references were not checked. Obtain confirmation on that target, then use `conductor integration delete <name>`. An agent may supply the CLI's yes flag after that confirmation. Verify absence; a 403 is not proof of deletion. Leave referencing definitions intact.

For create and update, ask for the environment variable’s name when a configuration field needs a credential. Write the literal reference as the whole field value, e.g. `{"configuration":{"api_key":"$.env.SERVICE_API_KEY"}}`. For rotation, send just the changed field in the patch. The CLI resolves the reference from its own environment. Pass it through unchanged in the JSON; never inspect, print, or expand the variable yourself. If the CLI rejects a reserved Conductor authentication variable, ask for the provider’s own credential variable. A provider-specific name such as `CONDUCTOR_INTEGRATED_APPS_STRIPE_KEY` is valid; do not copy Conductor credentials into another variable. If the CLI reports it is unset or empty, ask the user to set it in the environment that launches the CLI before retrying. If the user already prepared a protected file, pass its path directly. Avoid putting secrets in shell arguments, chat, workflow JSON or output. If a credential was pasted, direct the user to rotate it and supply the replacement securely.

## Integration tasks in workflows

For each `INTEGRATION` task, use the exact operation name for `name` and `inputParameters.method`. Set `integrationName` and `integrationType` inside `inputParameters` from the selected connection. Give the task a unique snake_case reference and bind the remaining inputs and any downstream outputs using the operation’s schema.

For a draft, show the definition without saving. For a create request, register it with `conductor workflow create <file>`, verify the saved version with `conductor workflow get <name> <version>`, and share its editor link. Running the workflow or activating a trigger requires a separate request.

When inspecting or editing a definition, follow integration references inside nested tasks and preserve existing connections and bindings outside the requested change. Before deleting a workflow, confirm the cluster, name, and version. The saved connection has its own lifecycle.
